The five things that must not be fudged:

- STOP PRECEDENCE. When both the goal is reached and the budget is spent, the
  reason MUST be "goal". A month-long run that ends by exhausting its budget on
  the very round that solved the problem would report success as exhaustion, and
  nobody would know the difference from the outside.
- NO-PROGRESS IS ONLY ABOUT REPEATS. `decideStop` must return
  stop/why="no-progress" only when the current round's outcome is identical to
  the previous one. The first round of a run (`previous` empty) must NOT be
  treated as no-progress even when `current` is also empty, because halting on
  round one would make an unattended system useless. Once rounds genuinely differ
  the loop keeps going.
- CRASH SURVIVORS ARE REQUEUED. A history entry whose status is "running" means
  the process died mid-round. Its tasks go into the `requeued` argument of the
  NEXT `runRound` call, and its round number must be passed to `markAbandoned`.
  The judge checks both. Rounds already "landed" or "failed" must NOT be requeued.
- PERSIST AS YOU GO. Call `saveState` at least once per round you actually run.
  An unattended process that persists only at the end loses the whole run to any
  crash, which is the entire failure mode S1 was written to prevent.
- RESPECT THE CEILING. `runRounds` must never run more than `maxRounds` rounds
  even if every round looks different and the budget check keeps saying false.

`sameOutcome` compares taskId, passRate and the produced-path list. A commit that
produced no files is a different outcome from one that produced the expected
file, and the judge pins that.
